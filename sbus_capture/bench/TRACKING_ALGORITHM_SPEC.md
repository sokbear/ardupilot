# Алгоритм захвата и сопровождения метки (целевое видение оператора)

Документ фиксирует **целевой** алгоритм сопровождения, согласованный с оператором,
сравнение с текущей реализацией `electronic_pilot_bench`, оценку реализуемости
на Pi 5 / OpenCV и вывод о целесообразности перехода.

Связанные файлы: `marker_tracker.*`, `config.h`, `main.cpp`.

**Реализация с 2026-07-03:** `MarkerTracker` (motion-refine + weighted NCC + adaptive template).
MOSSE/`BboxScaler` удалены; восстановление — git tag `epilot-snapshot-*`.

---

## 1. Целевой алгоритм (описание оператора)

### 1.1. Начальный захват

1. Оператор выделяет рамку вокруг объекта в кадре.
2. В начальный момент рамка может захватывать не только объект, но и часть
   **статического фона** за ним / вокруг него.
3. Требуется **автоматическая корректировка размеров** рамки до «чистого» объекта.

### 1.2. Корректировка рамки при движении

При перемещении объекта алгоритм:

1. Сравнивает **два или несколько кадров** за заданный интервал времени.
2. Выделяет область, которая одновременно:
   - **максимально статична внутри себя** (согласованное содержимое пятна);
   - имеет **максимальное смещение** в кадре за этот интервал (в отличие от фона).
3. По размерам найденной области **корректирует рамку**.
4. Запоминает область как **шаблон для корреляции**.
5. Корреляция выполняется с **весовыми коэффициентами**: от центра к краям вес
   снижается. Края шаблона вносят меньший вклад, чем центр — чтобы ослабить
   влияние высококонтрастного статичного окружения на границе ROI.

### 1.3. Адаптация шаблона и рамки во времени

Видимая сигнатура объекта меняется при удалении/приближении (масштаб), при изменении
угла обзора (перспектива, форма в кадре). Поэтому:

- шаблон и размеры рамки **постоянно подстраиваются** под текущую видимую сигнатуру;
- принимаются ограничения плавности:
  - **(а)** сигнатура не может измениться мгновенно (кроме ухода из кадра / перекрытия);
  - **(б)** положение не может измениться мгновенно (кроме ухода из кадра / перекрытия);
- в пределе: рамка от **точки** (максимальное удаление) до **почти всего кадра**
  (максимальное приближение).

## 2. Что реализовано сейчас (этап bench, MOSSE + BboxScaler)

### 2.1. Цепочка в коде

```
Оператор (мышь, PAL 720×576)
    → RoiSelector → ROI в координатах FullHD 1920×1080
    → MosseTracker::init(roi)
         ├─ BboxScaler::init — серый патч ROI как шаблон (как есть, без очистки фона)
         └─ cv::legacy::TrackerMOSSE::init
    → каждый кадр @60 Hz (track-поток):
         ├─ MOSSE::update → позиция (mosse_center)
         ├─ resolveTrackCenter — эвристики MOSSE vs matchTemplate vs pred=last_good+v·dt
         ├─ BboxScaler::responseAt / locateNear — корреляция TM_CCOEFF_NORMED
         └─ при публикации @25 Hz: BboxScaler::measureScale (matchTemplate на уменьшенном ROI)
    → DisplayHub → PAL-поток OSD
```

### 2.2. Сопоставление с целевым алгоритмом

| Требование (целевой алгоритм) | Текущая реализация | Совпадение |
|------------------------------|-------------------|------------|
| Ручной ROI оператором | `RoiSelector`, мышь на PAL | **Да** |
| Коррекция рамки от статического фона в ROI | Нет; весь прямоугольник ROI → шаблон | **Нет** |
| Выделение движущейся области по нескольким кадрам | Нет; нет optical flow / frame diff / motion mask | **Нет** |
| Весовая корреляция (центр важнее краёв) | Равномерный `matchTemplate` (TM_CCOEFF_NORMED) | **Нет** |
| Постоянное обновление шаблона | Шаблон **заморожен** с момента `init` | **Нет** |
| Плавное изменение положения (ограничение скачка) | Частично: `lock_velocity`, пороги в `config.h`, streak до SEARCH | **Частично** |
| Плавное изменение масштаба/сигнатуры | `measureScale` сглаживает `scale_target`, шаблон не меняется | **Частично** |
| Учёт перспективы / поворота объекта | Только изотропный масштаб (один коэффициент) | **Нет** |
| Отделение «уход из кадра / перекрытие» | FSM: Live → Predicted (SEARCH) → Lost, таймауты | **Частично** |

### 2.3. Почему текущий путь зашёл в тупик

Накопленные эвристики (MOSSE + замороженный шаблон + `locateNear` + предсказание
по скорости + маска drift + anti-latch) пытаются совместить **несовместимое**:

1. **MOSSE** оптимизирует корреляцию в Фурье-области и естественно тянется к
   **любому** устойчивому высококонтрастному паттерну в окне (статические края).
2. **Шаблон** снят с «грязного» ROI (объект + фон) и **не обновляется** — края
   шаблона буквально кодируют статику; любая корреляция по всему патчу усиливает
   зацеп за похожие края в кадре.
3. Добавление проверок «не доверять MOSSE» снижает зацеп, но **тормозит**
   сопровождение: позиция берётся с траектории шаблона / pred, а не с быстрого
   фильтра, при этом шаблон остаётся неверным.

**Вывод:** проблема не в «подкрутке коэффициентов», а в **архитектуре**: без этапа
очистки ROI и адаптивного взвешенного шаблона любые надстройки над MOSSE дают
компромисс «зацеп ↔ отставание».

## 3. Реализуемость целевого алгоритма

### 3.1. Используемый стек

| Компонент | Библиотека / средство | Примечание |
|-----------|----------------------|------------|
| Захват FullHD @60 | libcamera, `camera_capture.*` | Уже есть |
| Матричные операции, ROI | OpenCV core, imgproc | Уже есть |
| Корреляция | `cv::matchTemplate`, кастомный weighted NCC | Weighted — своей функцией |
| Оптический поток | `cv::calcOpticalFlowPyrLK`, `cv::calcOpticalFlowFarneback` | В OpenCV есть |
| Выравнивание / сдвиг | phase correlation, `cv::findTransformECC` | Для стабилизации пары кадров |
| Быстрый трекер (опционально) | MOSSE / KCF / CSRT (`opencv_tracking`) | Не обязателен в целевой схеме |
| Потоки track / PAL | `main.cpp`, `DisplayHub` | Сохраняются |

OpenCV **не содержит** готового «выдели движущееся пятно с максимальным смещением
и внутренней когерентностью» — это **собственный модуль** поверх flow / temporal diff.

### 3.2. Реализуемость по пунктам целевого алгоритма

#### П.1 — Коррекция начального ROI

**Реализуемо.** После фиксации ROI оператором:

- кратко подождать 1–2 кадра движения **или** попросить микродвижение;
- внутри ROI: optical flow между кадром t и t+Δt;
- пиксели с величиной смещения выше порога и связные → маска объекта;
- bbox маски → новая рамка; обрезка шаблона.

Если объект неподвижен в момент захвата — нужен fallback (центральная часть ROI,
или отложенная калибровка при первом движении).

#### П.2 — Весовая корреляция

**Реализуемо полностью на CPU.** Пример:

```
T_w(x,y) = T(x,y) · w(x,y),   w = Gaussian(σ ≈ 0.25·min(w,h))
NCC_w = Σ T_w·I_w / (||T_w||·||I_w||)
```

OpenCV `matchTemplate` напрямую не принимает веса — одна свёртка/цикл по ROI
достаточны; при поиске в окне 2×bbox на FullHD укладывается в бюджет @60 Hz,
если не гонять по всему кадру.

#### П.3 — Адаптивное обновление шаблона

**Реализуемо** с ограничениями плавности:

```
T_new = (1-α)·T_old + α·I_aligned,   α ≤ α_max(скорость изменения)
|center_new - center_pred| ≤ v_max·dt
|scale_new - scale_old| ≤ s_max·dt
```

Перспектива / поворот: на первом этапе — **изотропный масштаб** (как сейчас);
полный аффинный шаблон возможен через `warpAffine` + ECC, но дороже по CPU.

Гипотезы (а) и (б) — стандартный **gating** в фильтре состояния (или EMA с clamp).

### 3.3. Ограничения Pi 5 @ 1920×1080 @ 60 fps

| Операция | Оценка | Условие |
|----------|--------|---------|
| Dense Farneback на весь кадр | Скорее **нет** @60 | Только ROI 2–3× bbox |
| Sparse LK 50–200 точек в ROI | **Да** | Основной кандидат для п.2 |
| Weighted NCC в окне 256² | **Да** | Y-плоскость / gray |
| Обновление шаблона 64²–128² | **Да** | Каждый кадр или через кадр |
| MOSSE + matchTemplate + flow одновременно на FullHD | Риск **перегруза** | Заменить MOSSE, не добавлять |

Рекомендация: **один** трекинговый контур (motion-refined weighted template),
без параллельного MOSSE.

### 3.4. Совместимость с существующим кодом

| Модуль | Действие при переходе |
|--------|----------------------|
| `RoiSelector`, `main.cpp` (ROI, потоки) | **Оставить** |
| `DisplayHub`, `OsdRenderer`, PAL | **Оставить** |
| `GimbalTracker`, PID | **Оставить** (вход: ex, ey из bbox) |
| `MosseTracker` | **Заменить** или свести к тонкой обёртке |
| `BboxScaler` | **Переписать** → `AdaptiveTemplateTracker` |
| `marker_detector` | На стенде не используется (ROI вручную) |

Переход **не инкрементальный**: новый класс трекера + удаление эвристик
`resolveTrackCenter` / связки MOSSE+template.

## 4. Ожидаемый выигрыш в качестве

| Проблема сейчас | Даст ли целевой алгоритм улучшение |
|-----------------|-----------------------------------|
| Зацеп за статичные контрастные объекты | **Да**, если шаблон без фоновых краёв + веса к центру + обновление по движущемуся пятну |
| «Грязный» начальный ROI | **Да**, motion-based уточнение bbox |
| Отставание рамки при движении | **Да**, при отказе от тяжёлых anti-latch и быстром weighted NCC в окне pred |
| Масштаб при приближении/удалении | **Да**, непрерывная подстройка шаблона лучше разового `measureScale` @25 Hz |
| Поворот объекта в кадре | **Частично** на этапе 1 (только scale); полный affine — этап 2 |
| Перекрытие / уход из кадра | **Не хуже** текущего FSM; нужен порог по response |
| Стационарная метка после захвата | Нужен fallback без motion seg (центр ROI) |

**Итог:** описанный алгоритм **реализуем** на Pi 5 в рамках FullHD@60 при обработке
**локального окна** вокруг объекта; он **архитектурно соответствует** задаче лучше,
чем MOSSE + замороженный шаблон. Ожидается **существенный выигрыш** по зацепу и
отставанию, если принять переход как **замену ядра трекинга**, а не донастройку.

## 5. Предлагаемая архитектура (этап реализации)

```
ROI оператора
    → [MotionRefine] — 2–N кадров, sparse flow в ROI → bbox_obj, mask
    → [TemplateState] — T_gray, weights w, center, scale, velocity
    → каждый кадр @60 Hz:
         pred = center + velocity·dt
         (cx, cy, resp) = weightedNCC(search_window(pred), T, w)
         gate: |cx - pred| ≤ v_max·dt, resp ≥ τ
         α-обновление T из выровненного патча
         обновление scale по размеру маски / NCC pyramid
    → MarkerDetection → PID / OSD
```

MOSSE **не обязателен**; при необходимости быстрого pred — velocity из Калмана
или последних Δcenter.

## 6. Заключение

1. **Текущая реализация не соответствует** целевому алгоритму по ключевым пунктам:
   нет очистки ROI, нет весовой корреляции, нет адаптации шаблона.
2. Попытки исправить зацеп поверх этой архитектуры **ухудшили** сопровождение —
   это ожидаемо; тупик **методологический**, не «не те константы».
3. **Описанный оператором алгоритм реализуем** на Pi 5 + OpenCV с оговоркой:
   обработка только в окне объекта, Y/gray, изотропный масштаб на первом этапе.
4. **Выигрыш в качестве ожидается значительным** при полноценной замене ядра;
   дальнейшая настройка MOSSE+`locateNear` не рекомендуется.
5. **Следующий шаг:** реализовать `MotionRefine` + `WeightedTemplateTracker`,
   сохранить интерфейс `MarkerDetection` / `MosseTracker::update` для минимальных
   правок в `main.cpp`.
