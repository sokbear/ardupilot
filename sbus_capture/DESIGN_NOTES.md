# Журнал проектирования: удержание коптера по видео → «электронный пилот» (SBUS capture)

Документ фиксирует ход обсуждения, принятые решения и текущее состояние проекта,
чтобы не потерять контекст.

---

## 1. Исходный вопрос

Как в ArduPilot работает «удержание коптера по видео». Разобрали существующие
подсистемы технического зрения.

### Что есть в ArduPilot (итоги анализа кода)

| Подсистема | Где | Суть |
|---|---|---|
| **AC_PrecLand** | `libraries/AC_PrecLand/`, `ArduCopter/precision_landing.cpp`, `mode_loiter.cpp` | точная посадка / **Precision Loiter** — удержание над визуальной меткой |
| **FlowHold** | `ArduCopter/mode_flowhold.cpp`, `libraries/AP_OpticalFlow/` | удержание по оптическому потоку без GPS |
| **AP_VisualOdom** | `libraries/AP_VisualOdom/` | внешняя навигация (VIO) в EKF |
| **FOLLOW** | `ArduCopter/mode_follow.cpp`, `libraries/AP_Follow/` | следование за другим MAVLink-аппаратом по GPS |

Отдельного режима «слежение за произвольным объектом на видео» нет. Ближайшее —
**Precision Loiter** (удержание над меткой через `AC_PrecLand`).

### Как работает Precision Loiter / PrecLand

1. Внешний модуль зрения (компаньон-ПК или IR-Lock) шлёт направление на метку:
   - `LANDING_TARGET` по MAVLink — обычно **углы** `angle_x/angle_y`
     (`position_valid=0`), реже 3D-координаты `x,y,z + distance`.
   - Контроллер сам сводит всё к **вектору направления (LOS) + дальность**.
2. Вектор разворачивается из системы корпуса в NED через матрицу AHRS `Tbn`.
3. Дальность берётся от **дальномера-вниз** (или из `distance` датчика):
   `dist = h / cos(θ)`.
4. Позиция метки фильтруется мини-EKF (фьюз с акселерометром, компенсация лага).
5. `ModeLoiter::precision_loiter_xy()` подаёт позицию в **горизонтальный**
   контроллер положения (`input_pos_vel_accel_NE_m`). Приоритет — у пилота.

Ключевые файлы: `AC_PrecLand.cpp` (`run_estimator`,
`construct_pos_meas_using_rangefinder`, `run_output_prediction`),
`AC_PrecLand_MAVLink.cpp` (`handle_msg`), `mode_loiter.cpp`.

## 2. Цепочка вопросов и выводов

1. **Данные от модуля — это 3D-координаты?** Нет. Чаще это **углы** (направление);
   3D-координаты — опциональный формат, и их всё равно сводят к «направление +
   дальность».

2. **Можно ли без дистанции, просто держа метку в центре кадра?**
   Теоретически да (IBVS, для камеры-вниз это чисто угловая задача), и в
   ArduPilot такой принцип уже есть в **FlowHold**. Но штатный `AC_PrecLand`
   **требует дальность** (без неё `construct_pos_meas...` возвращает false).

3. **Метка не под коптером, а впереди/выше — сработает?**
   - Впереди/сбоку **на земле** — да (проекционная геометрия `h/cos θ`).
   - **Выше коптера** — нет: камера-вниз не видит, проверка направления
     отбрасывает, дальномер неприменим, Precision Loiter рулит только горизонтом.

4. **Следовать за меткой в произвольной 3D-точке (камера вверх)?**
   Штатным PrecLand — нет. Нужно: (а) дальность (AprilTag/ArUco известного
   размера дают 6DOF-позу), (б) полное 3D-управление. Варианты: компаньон-ПК +
   Guided (`SET_POSITION_TARGET_LOCAL_NED`) или кастомный режим на базе FOLLOW
   (он уже умеет NE+D+yaw).

5. **Переложить роль ОПЕРАТОРА на малину** (оператор держит метку в центре
   стиками) — **выбранная концепция**. Это IBVS: малина по пиксельной ошибке
   двигает «стики». Дистанция и NED не нужны (как и живому оператору).

## 3. ВЫБРАННАЯ архитектура: SBUS man-in-the-middle

```
TBS Nano (RX) --SBUS--> [ Raspberry Pi: sbus_capture ] --SBUS--> Полётник (ArduPilot)
                              ^ камера (стабилизирована гимбалом по pitch+roll)
```

Полётник **не дорабатывается** — для него это обычный SBUS-вход.

### Два режима
- **Прозрачный** — кадры оператора ретранслируются в FC 1:1.
- **Захват** — малина формирует CH1/CH2 (roll/pitch) из видео-PID; CH3/CH4
  (газ/рыскание) и все AUX — от оператора. Активируется тумблером с пульта.

---

## 4. Зафиксированные решения

1. **Каналы:** CH1 roll, CH2 pitch, CH3 throttle, CH4 yaw, CH5 flight mode,
   **CH7 — тумблер режима «захват»**, **CH8+ — команды/механизмы**.
2. **Разделение в захвате (итоговое):**
   - **Автоматика (малина → RP2040):** roll, pitch, yaw (`ex → yaw`, азимут),
     throttle (внешний контур анти-сатурации гимбала / удержание высоты).
   - **Оператор всегда:** переключение режима (CH7), AUX/механизмы (CH8+),
     приоритетный перехват (CH7=OFF снимает захват немедленно).
   - Каналы оператора (CH7, CH8+) RP2040 пробрасывает без изменений в любом режиме.
   - Схема управления: `ey → уставка β гимбала` (быстрый внутр. контур, держит метку
     по вертикали); коптер pitch/throttle — медленный внешн. контур (анти-сатурация
     гимбала, удержание высоты/дальности); `ex → yaw` (азимут); roll гимбала = только
     стабилизация горизонта (уставка 0, pitch гимбала — активная ось слежения).
3. **Переключение режима — только тумблером CH7.** Авто-возврат по стику —
   выключенный хук на будущее (`ENABLE_STICK_OVERRIDE=false`).
4. **Аппаратный failsafe-mux — пока не нужен.** При потере пульта малина
   пробрасывает флаг failsafe → срабатывает штатный failsafe FC.
5. **Гимбал — Вариант B:** двухосевая стабилизация **pitch+roll от полётника**
   (штатный `AP_Mount_Servo`, дешёвые сервы, гиро-упреждение `*_stb_lead`).
   Активный трекинг гимбалом на малине отвергнут (дублирует AHRS FC, медленный
   видео-контур плохо давит порывы). Стабилизированная камера ⇒ `ex,ey` = чистый
   угловой пеленг.
6. **Режим коптера в захвате:** AltHold/Stabilize (стик = угол наклона).
7. **Дистанция не важна** (только центрирование = направление).
8. **Язык:** C++17.

### Технические факты по SBUS (из кода ArduPilot)
- 100000 бод, **8E2, инвертированный сигнал** (`SERIAL_CONFIG_8E2I`).
- Кадр 25 байт: `0x0F` + 16×11 бит (22 байта) + флаги(байт 23) + `0x00`.
- Флаги: бит2 frame_lost, бит3 failsafe.
- **«Мягкий failsafe»:** FC считает кадр failsafe, если любой из каналов 1–4
  `≤ 875us` (raw ≤ 0). Управляемые малиной каналы зажимаем в безопасный коридор.
- Межкадровый разрыв `HAL_SBUS_FRAME_GAP = 2000us`.

### Оценка задержек (малина в разрыве)
- 1 байт = 12 бит = 120 µs; кадр (25 байт) = 3 мс «на проводе»; период 7–14 мс.
- Добавочная задержка малины при аккуратной реализации **~3–6 мс**
  (худший случай с джиттером ~10–15 мс) — против ~200 мс реакции человека.
- Узкое место — **джиттер Linux**, не пропускная способность. Митигации:
  аппаратный UART (не USB), `SCHED_FIFO`, изоляция ядра. Видео-контур ~30–60 Гц
  развязан от TX-потока.
- Pi-only годится для прототипа; для боевой версии SBUS можно вынести на МК.

## 5. Текущее состояние кода (`sbus_capture/`)

Standalone-проект для Raspberry Pi (не часть прошивки). Линтер чистый.
Собирать **на малине** (`make`) — код Linux-специфичный.

| Файл | Роль |
|---|---|
| `config.h` | каналы, пороги, тайминги, пределы SBUS, усиления PID, калибровка осей |
| `sbus.h/.cpp` | кодек кадра SBUS (decode/encode) |
| `serial_port.h/.cpp` | UART 100000 8E2 через `termios2` |
| `shared_state.h` | потокобезопасный обмен RX/Vision/TX |
| `pid.h` | PID с ограничением и анти-виндапом |
| `vision.h/.cpp` | **заглушка** детектора метки (точка подключения OpenCV/AprilTag) |
| `control.h/.cpp` | конечный автомат режимов + генерация SBUS (RT-поток) |
| `main.cpp` | связывание портов/потоков, чтение приёмника со сборкой кадров |
| `Makefile`, `README.md`, `.gitignore` | сборка и документация |

### Конечный автомат (`control.cpp`)
- `TRANSPARENT` → `CAPTURE`: CH7=ON **и** метка видна.
- `CAPTURE` → `TRANSPARENT`: CH7=OFF, или метка потеряна `> VISION_LOST_US`,
  (опц.) override по стику.
- любое → `FAILSAFE_PASS`: failsafe от RX или таймаут; проброс failsafe в FC.

## 6a. Камера, метка и дальность детекта

### Правильная метрика — «пиксели на метке», не мегапиксели
\[ n = \frac{M}{D}\cdot\frac{W}{\text{FOV}}, \quad N_{\min}:\ \text{детект ~30 px (узор), ~5–10 px (силуэт), удержание — субпиксельно} \]
Где M — размер метки, D — дистанция, W — горизонт. разрешение, FOV в радианах.

### Заданные параметры
- Размер метки: **1.5 м**, пассивная (активный маяк **исключён**).
- Фон — **небо** ⇒ высокий контраст ⇒ силуэтный детект (низкий \(N_{\min}\)).
- Камера: **1280×720** (ограничение: ни длиннофокус, ни сверхразрешение).
- **Целевая дистанция: 500 м.**

### Почему 1–1.5 км отпало
При 720p и не-телефото объективе пассивная метка детектится на десятки–сотни м.
Для 1500 м надёжно нужен FOV ≈ 2.4° (телефото ~90–180 мм) — отвергнуто.
Без активного маяка километр на 720p недостижим.

### Дальность при 720p, метка 1.5 м (\(D_{\max}=64/\text{FOV(рад)}\) для 30 px)
| FOV | D надёжно (30 px) | D маргинально (20 px) |
|---|---|---|
| 60° | 61 м | 92 м |
| 30° | 122 м | 183 м |
| 15° | 244 м | 367 м |
| 10° | 367 м | 550 м |

### Решение для 500 м (силуэт на фоне неба, \(\text{FOV}=1920/(N_{\min}\cdot500)\))
| Режим / \(N_{\min}\) | FOV | Фокусное (~3µm) |
|---|---|---|
| декод узора 30 px | 7.3° | ~30 мм |
| силуэт 10 px | **22°** | **~10 мм** |
| силуэт 8 px | 27.5° | ~8 мм |

**Выбранная конфигурация:** 1280×720, глобальный затвор, 30–60 fps, объектив
**FOV ~20–25° (≈8–11 мм)**. Метка — **сплошная матовая высококонтрастная фигура**
1.5 м (диск/шар), НЕ мелкий ArUco: нужен только центроид (пеленг), ID/ориентация
не требуются. Угловое разрешение ~0.3 мрад/px, запас по детекту до 500 м.

### Оговорки (фон неба)
Ложные цели (птицы/облака) → временной трекинг + гейтинг по размеру/форме/скорости;
солнце в кадре → бленда; метка ниже горизонта ломает силуэт; пасмурно снижает
контраст; обязателен глобальный затвор + короткая выдержка против смаза.

## 6b. Тип камеры и интерфейс ввода в малину

### Решение: аналоговая FPV-камера с разветвлением сигнала
MIPI-камера отвергнута (дорого + вопрос низколатентной передачи оператору).
Выбран аналоговый тракт:

```
FPV-камера (CVBS) ──┬──> аналоговый VTX ──радио──> оператор (очки)
                    └──> оцифровщик ──> Raspberry Pi (детект)
```

- Оператор идёт по **чистому аналоговому FPV** (камера→VTX→RX), малина НЕ в тракте
  ⇒ задержка оператора классическая FPV (<20–40 мс), от Pi не зависит. Опасение
  по латентности первичного захвата снято.
- Разветвление — буферным видео-сплиттером (или VTX loop-through).

### Оцифровка CVBS в Pi (два варианта)
1. **USB-граббер CVBS→USB (UVC)** — чипы MS2109/UTV007/EM28xx, V4L2/OpenCV
   напрямую. Дёшево (~$10), plug-and-play, но +50–150 мс задержки. Для прототипа.
2. **ADV7282-M (CVBS→MIPI CSI-2)** — мост в CSI-порт, низкая задержка, чисто.
   Для боевой версии. Нужен device tree overlay.

### Поправка на разрешение (аналог < 720p)
Композит PAL ~720×576 (i), NTSC ~720×480 (i). Пересчёт для 500 м, метка 1.5 м,
силуэт (W=720): FOV = 1.5·720/(N_min·500).
| \(N_{\min}\) | FOV для 500 м | Дальность при FOV 22° |
|---|---|---|
| 10 px | ~12.4° | ~280 м |
| 8 px | ~15.5° | ~350 м |
Компромисс: либо FOV ~12° для 500 м, либо широкий ~22° и дальность ~280 м.

### Нюансы аналога
Чересстрочность → деинтерлейс (одно поле/bob); шум аналога — но фон неба даёт
огромный контраст, силуэтный детект устойчив. Подтверждает выбор блоб-детектора
в `vision.cpp` (а не чтение узора ArUco).

### Оцифровщик: только Analog→MIPI CSI (USB-граббер исключён, 150+ мс)
USB UVC-граббер отвергнут из-за задержки. Выбран мост CVBS→MIPI CSI-2.

**Чипы:** Analog Devices **ADV7280-M / ADV7282-M** (штатный драйвер в ядре RPi,
`adv7180.c`); альтернативы — Renesas **TW9992**, ROHM/LAPIS **ML86112**.
ВАЖНО: брать вариант **`-M` с I2P-деинтерлейсером** (ADV7280-M/7282-M), т.к. Pi
не принимает чересстрочное по CSI; `ADV7281-M` (без I2P) не подходит.

**Готовые платы под Pi:**
- e-zsche/ADV7280-Raspi-shield (откр. HW, plug'n'play, пинаут как у камеры Pi)
- rniwase/sdtv2csi (откр. HW, ADV7280A-M, скрипты под RPi4, обновл. 2025)
- antmicro/cvbs-mipi-bridge (откр. HW, ADV7282-M, больше под Jetson)
- Oppila PAL→MIPI (коммерч., под Jetson Orin), ADI EVAL-ADV7282-M (eval)

**Задержка:** сам чип ≈ 0 (20–100 пиксел. тактов, деинтерлейс ≤3 строк). Цифра
~130 мс из форумов — это тракт С ВЫВОДОМ НА ДИСПЛЕЙ. У нас headless → OpenCV,
raw-захват V4L2: реально **~40–80 мс (1–2 кадра PAL)**, детерминированно.
Оператора не касается (он на чистом аналоге).

### Обратный вариант MIPI камера → аналог (рассмотрен, отвергнут)
Чип есть: Renesas **RAA279971** (MIPI CSI-2 in → CVBS out, 10-бит ЦАП, до
720p60/1080p30); классич. энкодеры ADV7391/ML86640 требуют параллельный вход.
НО: MIPI — point-to-point, **пассивно не разветвить**. Любой обратный путь либо
гонит видео оператора ЧЕРЕЗ малину (та самая задержка), либо требует
MIPI-репликатор (FPGA, дорого). Решение: **остаёмся на прямом тракте
аналог→ADV728x-M→CSI**; обратный — только если позже нужно качество MIPI.

### Открытые вопросы
- PAL (576i/25) или NTSC (480i/30)?
- Приоритет: сохранить 500 м (FOV ~12°) или шире обзор (~22°, ~280 м)?

## 6c. Потолок разрешения: HD-аналог и цифровой линк

### Потолок CVBS — это SD (свойство стандарта, не камеры/чипа)
Композит PAL ~720×576i / NTSC ~720×480i — предел из-за полосы сигнала (~5–6 МГц).
TVL — это резкость в пределах SD; CVBS режет реальную детализацию ~560–570 TVL,
«1200 TVL» — маркетинг. ADV7282-M тоже SD-only, но **бутылочное горлышко — сам
CVBS**, не чип. Для PAL берём PAL (576 > 480).

### HD-аналог (HD-over-coax) — выше SD, но НЕ классический FPV
Стандарты **AHD / HD-TVI / HD-CVI** несут 720p/1080p (AHD до 5–8 Мп) по коаксиалу.
Мосты в MIPI CSI-2 — чипы **Techpoint**:
| Чип | Каналы | Форматы | Разрешение |
|---|---|---|---|
| TP9950 | 1 | TVI/AHD/CVBS | до 1080p25/30 |
| TP2860 | 1 | TVI/AHD/CVI/CVBS | 1080p/720p/D1 |
| TP2855 | 4 | TVI/AHD/CVI/CVBS | до 1080p60/50 |
**НО:** классический аналоговый FPV-VTX передаёт только CVBS (SD). AHD/TVI обычный
FPV-передатчик НЕ транслирует ⇒ при HD-аналоге придётся менять тракт оператора
(отдельный CVBS-feed = опять SD, либо цифровой HD-линк). Пассивное разветвление
«оба видят один низколатентный сигнал» держится только на SD CVBS.

### Цифровой линк (вариант к рассмотрению) — OpenIPC / IPC-камеры
Идея: IP-камеры на SoC вроде **GOKE GK7205** (и Hisilicon HI3516) под Linux,
открытая прошивка **OpenIPC**. Дают HD (720p/1080p) по цифре.

Замечание пользователя по слабому месту — радиоканал на обычном WiFi-стеке
(накладные расходы + прослушивание канала на TX). Проверено: это адресует
**wfb-ng (wifibroadcast)**, на котором и построен OpenIPC FPV:
- monitor mode + инъекция пакетов, **без ассоциации, без ACK, без ретрансмита**;
  вместо ретрансмита — **FEC**; 1:1 RTP→802.11 для мин. задержки.
- НО: сам wfb-ng не делает CSMA/CA backoff, однако **железный carrier-sense (CCA)
  чипа может оставаться** (зависит от драйвера/карты) — концерн пользователя снят
  в основном, но не на 100% на уровне железа.
- Латентность glass-to-glass у оптимизированных OpenIPC/Majestic ~**60–100 мс**
  (H.264/H.265 энкод+декод) — против ~0 у аналога. Это плата за HD/цифру.
- Карты: RTL8812AU и т.п. в monitor mode; несёт видео-вниз + MAVLink, RC.

**Архитектурный плюс для нашего проекта:** радиолинк нужен только для передачи
видео ОПЕРАТОРУ (первичный захват). Детект работает на ЛОКАЛЬНЫХ кадрах на борту,
поэтому задержки/потери радио на контур удержания НЕ влияют. Более того, SoC
IPC-камеры (Linux) потенциально может сам хостить детект (наш блоб-детектор лёгкий)
и даже SBUS-логику — возможно, без отдельной малины (нужна проверка ресурсов
GK7205: слабый SoC, но задача лёгкая).

Условие пользователя: цифровой вариант интересен, ЕСЛИ решить проблемы радио
(wfb-ng в значит. степени решает) — держим как реальную альтернативу аналогу.

## 6d. Можно ли убрать малину: детект+SBUS на SoC камеры

### Нагрузка задачи — лёгкая
- SBUS-MITM: 2×UART @100к, 25 байт/14мс, CPU <1%. Риски: наличие 2 UART, HW-инвертор,
  RT-детерминизм TX на загруженном Linux.
- Блоб-детект (силуэт на небе): порог+связные компоненты+центроид по Y-плоскости,
  единицы мс/кадр с NEON. Энкодер аппаратный → ядра свободны. Сложность: доступ к
  YUV-кадру из пайплайна OpenIPC (MI/IVE SDK, NDA) + rolling shutter IPC-сенсоров.

### OpenIPC-FPV SoC (с wfb-ng)
| SoC | Ядра | RAM | NPU |
|---|---|---|---|
| GK7205V200 | 1×A7 | 64/128 МБ | нет |
| GK7205V300 | 1×A7 | до 128 МБ | нет |
| Hi3516EV300 | 1×A7 | 64/128 МБ | нет (лучшая поддержка ядра 6.6 LTS) |
| **SSC338Q** | **2×A7 @1.2ГГц NEON/FPU** | **256 МБ** | **0.5 TOPS DLA+IVE** |
SSC338G/339G — 1 TOPS, но без встроенной RAM. Выше (A53/A55, до 3 TOPS) — НЕ
стандартные OpenIPC-FPV таргеты (потеря готового wfb-ng).

### Вердикт
GK7205 как all-in-one не брать (RAM/одно ядро). **Цель — SSC338Q-класс**: тянет
камеру + wfb-ng + детект с запасом (для блоба NPU избыточен, пригодится для CNN).

### Рекомендуемая архитектура (без малины)
SSC338Q (OpenIPC): ISP+сенсор → H.265+wfb-ng оператору → блоб-детект на Y-плоскости.
**Крошечный МК (STM32/RP2040 ~$2) — SBUS-MITM детерминированно**, общается с SoC по
UART («каналы + режим»). Убирает малину, держит SBUS-тайминг железно, детект на
локальных pre-encode кадрах (мин. задержка, не зависит от радио).
Альтернатива «всё на SoC» (SBUS на 2×UART SoC + инвертор) — возможна, но RT-тайминг
рискованнее.

### Проверить перед выбором
1. Доступ к YUV из OpenIPC/Majestic (MI/IVE; SDK SigmaStar под NDA). → см. 6e.
2. Свободные UART под МК (и/или 2×UART для SBUS) + аппаратный инвертор.
3. Rolling shutter сенсора (IMX307/335/415) — смаз; GS в IPC почти нет.
4. Тулчейн ARMv7 (musl/uClibc); OpenCV тяжёл — лучше лёгкий C или IVE.

## 6e. Доступ к YUV-кадрам в OpenIPC — ПРОРАБОТАНО

### Вердикт: реально, низколатентно, но через вендорный MI-SDK (не «из коробки»)

**Три уровня доступа:**
1. HTTP Majestic: `image.yuv420`, `image.jpg?...&color2gray=1`, `/mjpeg`, RTSP —
   pull-снапшоты/сжатый поток. Только для ОТЛАДКИ алгоритма (лаг/частота не для

2. Встроенный motion detect Majestic — разностный, отдаёт лишь счётчик объектов

3. **Своё MI/VPE-приложение (правильный путь):** VPE имеет 3–4 выходных порта;

   задержка). **NV12: Y-плоскость = готовый grayscale** для силуэта (UV игнор).

**Подводные камни:**
- SDK SigmaStar MI под NDA: либы `libmi_sys/vpe/ive.so` ЕСТЬ в рабочей прошивке

- Majestic (закрытый бинарник) владеет пайплайном VIF→VPE→VENC. Делить хрупко →

- SoC-специфика: SigmaStar = MI API; HiSilicon/Goke = HiMPP (HI_MPI_VPSS_GetChnFrame).

**Итог:** барьер интеграционный (SDK + свой MI-пайплайн), не вычислительный.
Выполнимо (комьюнити делает), но реальный объём работы — в отличие от V4L2 на малине.
Прототип: сперва `image.yuv420`/MJPEG для валидации детектора, затем перенос на MI.

## 6f. Выбор платы Raspberry Pi и вопрос ИИ-ускорителя

Основной путь — малина (вариант «всё на камере» — про запас, см. 6c–6e).
По вычислениям задача тривиальна для всех → выбор по UART/размеру/питанию/CSI.

### Критично: SBUS=8E2, parity умеет только PL011
mini-UART НЕ поддерживает чётность. На Pi 3/Zero на GPIO14/15 доступен только один
порт (PL011 или mini) = 1 parity-линия. Нам нужно 2× 8E2 (RX приёмника + TX в FC).

| Модель | Вычисл. | Нативно 2×8E2 UART | Размер/питание | CSI/мост |
|---|---|---|---|---|
| Pi 5 | избыток | Да (4×PL011, нет mini) | большой, ~5–8Вт, обдув | adv7280 через Media Controller |
| Pi 4 | избыток | Да (PL011 ×неск.) | большой, прожорлив | adv7282m просто |
| CM4 | избыток | Да (6 UART) | компактный на носителе | 2×CSI |
| Zero 2 W | достаточно (4×A53/512МБ) | НЕТ (1×PL011) | мин. ~1–2Вт ~11г | mini-CSI (переходник) |

Инвертор SBUS на обе линии нужен в любом случае (у UART Pi инверсии нет).

### Ключ: SBUS на отдельном МК снимает вопрос UART
Если SBUS вынесен на МК (STM32/RP2040, как в боевом варианте): Пи не нужны
parity-UART (МК держит обе линии, связь с Пи по 1 UART/USB). Бонусы: детерминизм
тайминга; многие МК инвертируют UART аппаратно (STM32 штатно, RP2040 через PIO) →
внешний инвертор может стать не нужен.

### РЕКОМЕНДАЦИЯ
- **Предпочтительно: Pi Zero 2 W + крошечный МК для SBUS** — мин. размер/вес/питание,
  вычислений с запасом, CSI для моста, ограничение 1×PL011 обходится через МК.
- Если «всё на Пи без МК»: **Pi 5** (неск. PL011, нет mini; но крупнее/греется,
  adv7280 через media-ctl) или **CM4** (6 UART, компактен — лучший all-on-Pi).
  Pi 4 рабочая, но устаревает.

### ИИ-ускоритель — НЕ нужен
Детект = классический CV (порог + связные компоненты по Y), единицы мс на CPU.
Hailo AI HAT+ (13–26 TOPS) нужен только для нейросетей (сложный фон, бесмаркерно,
много классов) и работает только с Pi 5 (PCIe). Держим как будущую опцию (если
детект придётся переводить на CNN: Pi 5 + AI HAT).

## 6g. RP2040-плата: SBUS + UART (РЕШЕНО)

### Решения
- Два UART SBUS реализуются на **RP2040 (PIO)**: инверсия + 8E2 + детерминированный
  тайминг штатно. Снимает ограничение Pi на parity-UART (см. 6f).
- **Всё, что касается SBUS и UART — на RP2040:** 2×SBUS (PIO), FSM прозрачный/захват,
  MAVLink-телеметрия с FC, линк с малиной. Pi в SBUS/UART к FC **не участвует**.
- **OSD — на малине, графическое** (см. §6i): MAX7456 и SPI на RP2040 **не нужны**.
- Архив (отвергнуто): RP2040 + MAX7456 (символьный OSD), PIO-оверлей LM1881.

### Раскладка портов RP2040
- PIO ×2 SM: SBUS RX (приёмник) + SBUS TX (полётник).
- UART0 (hw): MAVLink-телеметрия от полётника.
- UART1 (hw): линк с малиной.
- SPI / MAX7456: **не используются**.

### Интерфейс малина ↔ RP2040 (UART 921600 8N1, бинарный кадр + CRC16)
Малина → RP2040 (~30–60 Гц):
```
[0xA5][len][type][payload][crc16]
type=0x02 CONTROL:  mode u8, roll u16, pitch u16, throttle u16, yaw u16  (CH1–CH4)
type=0x03 HEARTBEAT: seq u8, pi_status u8
```
RP2040 → малина:
```
type=0x81 RC_STATUS: ch7 u16, failsafe u8, link_ok u8
type=0x82 TELEM:     parsed MAVLink fields для граф. OSD на Pi
```
seq+CRC; при таймауте пакетов малины RP2040 выходит из захвата (прозрачный режим).
OVERLAY (type=0x01) **убран** — рамка рисуется на Pi; RP2040 парсит MAVLink и шлёт TELEM.

### Оговорки
1. Pi один PL011 → единственный UART к RP2040 (отладка USB/SSH).
2. Задержка детекта ~40–80 мс → рамка OSD слегка отстаёт; опц. предсказание по скорости.
3. RP2040: HW-UART 2/2, PIO 2/8 SM, GPIO ~8/26 — с запасом (без SPI/OSD).

## 6i. MIPI-камера + графический OSD на Pi (РЕШЕНО)

### Решения
- **ADV7280-M и аналоговый сплиттер — убраны** (на текущем этапе). Одна **MIPI-камера**
  (IMX219 / IMX477 / совместимая) → Pi через CSI.
- **Picamera2 / libcamera — два потока с одного сенсора:**
  - **main** — макс. разрешение/fps для детекта метки;
  - **lores** — 720×576 @ 25 fps (PAL) для операторского тракта.
- **Графический OSD на Pi:** композитинг на lores-кадре (OpenCV/NEON): рамка метки,
  телеметрия (TELEM от RP2040), статус захвата, предупреждения.
- **CVBS для VTX** — после OSD: TV-out (Zero 2 W, достаточно) или **ADV7391** (стабильный
  уровень сигнала; задержка не критична — см. ниже).
- **Телеметрия для OSD:** FC → UART → **RP2040** (MAVLink) → UART → Pi (TELEM).
  Pi **не** подключается к FC по UART напрямую.

### Назначение операторского видеоканала (важно)

**Основная функция системы — захват и сопровождение метки** (режим CH7=ON). В этом
режиме CH1–CH4 полностью у автоматики; оператор **не управляет** полётом по видео —
только CH7 (вкл/выкл захвата) и CH8+ (AUX).

Поэтому **задержка в канале «Pi → VTX → оператор» не критична** для замкнутого контура
удержания: контур замкнут локально (main-поток → детект → Pi → RP2040 → SBUS), радио
и CVBS-задержка на него **не влияют** (аналогично OpenIPC/wfb-ng в §6e).

**Зачем тогда оператору видео?** Не для ручного пилотирования в захвате, а как **канал
наблюдения и отладки ПО**:
- оператор (или инженер на земле) **оценивает качество работы алгоритма** — держится ли
  метка в центре, адекватна ли рамка OSD, нет ли ложных срабатываний, срыва захвата;
- графический OSD (рамка + телеметрия + статус) даёт **визуальную обратную связь** при
  настройке PID, порогов детекта, логики FSM;
- в **прозрачном** режиме (CH7=OFF) оператор управляет вручную — тогда низкая задержка
  видео приятна, но это **не штатный боевой режим** системы.

**Следствие для проектирования:** TV-out с задержкой 80–150 ms — **приемлем** для v1;
ADV7391 — улучшение качества сигнала (уровень, синхро), а не обязательное требование
по задержке. Критична задержка **детектного** контура (main stream), не операторского.

### Видеотракт
```
MIPI-камера ──CSI──► Pi
                        ├─ main  → детект (ex, ey, bbox)
                        ├─ lores → граф. OSD (bbox + TELEM от RP2040)
                        └─ CVBS (TV-out / ADV7391) ──► VTX ──► оператор

TBS Nano ──SBUS──► RP2040 ──SBUS──► FC
                      │ UART MAVLink ◄── FC
                      │ UART линк ◄──► Pi (CONTROL + TELEM + STATUS)
```

### Нагрузка и железо
- Zero 2 W — **на пределе**. **Pi 4 / CM4** — комфортный запас.
- Графический OSD на 720×576 — ~1–3 ms/кадр.
- Операторский тракт **зависит от Pi** — при падении Pi теряется мониторинг/отладка,
  но SBUS-контур (RP2040) и замкнутое удержание продолжают работать, пока Pi жива
  или до failsafe по таймауту линка Pi↔RP2040.

## 8. ИТОГОВОЕ РЕШЕНИЕ (проверено по ресурсам — PASS)

### Поправка по потокам данных
Малина **не на SBUS и не на UART к FC**. TBS-nano → SBUS → RP2040 → SBUS → FC
(подмена CH1–CH4 в захвате). Малина ↔ RP2040 — UART (CONTROL + TELEM + STATUS).
«Эмуляцию стиков» физически делает RP2040 по данным малины. Инверсия — в PIO RP2040
(внешний инвертор не нужен). Конечный автомат прозрачный/захват — на RP2040 (у него
кадры SBUS + CH7); ранее написанный sbus_capture (C++) = референс-логика для прошивки.

### Проверка ресурсов (узких мест нет)
RP2040: HW-UART 2/2 (MAVLink FC + линк малины); PIO 2/8 SM (SBUS RX+TX); GPIO ~8/26;
264КБ/2×M0+@133МГц — с запасом (SPI/MAX7456 не используются).
Pi 4 / CM4 (рекоменд.): CSI ×1 (MIPI-камера); UART ×1 (линк к RP2040); dual-stream +
граф. OSD + CVBS. Zero 2 W — возможно при снижении main-res/fps.
FC: 1×RC-in SBUS, 1×telem-UART (MAVLink), 2×PWM (гимбал) — стандартно.

### Мелкие вопросы (не блокеры) + решения
1. CVBS: v1 — **TV-out** (test pads, достаточно: задержка оператору некритична); v2 —
   ADV7391 для стабильного уровня/синхры, не ради задержки.
2. Pi один PL011 → линк только к RP2040; отладка USB-gadget/SSH.
3. Отставание рамки OSD от метки (детект 40–80 мс) → для **отладки алгоритма** видно
   глазом; на 500 м при крейсерском режиме допустимо; опц. предсказание bbox.
4. Чистый 5В BEC + общая аналоговая земля (камера/CVBS-DAC/VTX).
5. Rolling shutter MIPI-модуля — короткая выдержка / GS-модуль при смазе.

### Состав и роли (финал)
- FC ArduPilot: AltHold/Stabilize; стабилизация камеры pitch+roll (AP_Mount, 2 серво);
  управление по SBUS. `ATC_ANG_MAX=55°`, `ARMING_SKIPCHK` бит INS (16).
- Камера: **MIPI CSI** (RGB/GS) на 2-осевом серво-гимбале. Угол установки на раму ~**70°**
  (от плоскости рамы, нос вверх; наклонный старт). Ход гимбала: pitch **30°** (серво
  55°…85° отн. рамы), roll **±20…25°**.
- Детект: MIPI → Pi main stream (силуэт / blob → центроид + bbox).
- Оператор: Pi lores → **граф. OSD** → CVBS → VTX — **мониторинг качества захвата**
  и отладка ПО (не канал ручного управления в режиме захвата).
- RP2040: 2×SBUS на PIO (инверсия+8E2), FSM прозрачный/захват по CH7,
  подмена CH1–CH4 в захвате; UART к FC (MAVLink parse) и к малине (CONTROL/TELEM/STATUS).
- Малина: CV + CONTROL overrides + **граф. OSD** + CVBS out; в SBUS/UART к FC не участвует.

### Разделение управления (финал)
| Ось / канал | Захват | Примечание |
|---|---|---|
| Roll (CH1) | Автоматика | видео-PID по горизонт. ошибке |
| Pitch (CH2) | Автоматика | внешний контур анти-сатурации гимбала |
| Throttle (CH3) | Автоматика | удержание высоты/дальности (внешний контур) |
| Yaw (CH4) | Автоматика | `ex → yaw`, удержание азимута метки |
| Режим FC (CH5) | Оператор | проброс |
| Тумблер захвата (CH7) | Оператор | читается всегда; OFF → немедл. выход |
| AUX (CH8+) | Оператор | проброс без изменений |

Возврат — CH7=OFF; потеря пульта → RP2040 пробрасывает failsafe в FC; потеря линка
малины → выйти из захвата (прозрачный режим).

### Резерв на будущее
Цифровой линк (OpenIPC/wfb-ng) + детект на SoC камеры (SSC338Q) — отложено.

## 6h. Ориентация и углы камеры/гимбала, связь со скоростью (РАСЧЁТ — ФИНАЛ)

### Обозначения
- Оси рамы: **X — вперёд, Y — вправо**; pitch = поворот вокруг Y, roll = вокруг X.
- **θ** — наклон рамы носом вниз (создаёт горизонт. тягу).
- **β** — угол места оптической оси над горизонтом (управляемая уставка гимбала).
- Серво гимбала по pitch отн. рамы = **β + θ**.

### Зафиксированные параметры сценария
- **`ANGLE_MAX = 55°`**, **T/W = 10:1**.
- **Наклонный старт:** армирование при **θ = 55°** (нос вниз), без фазы висения и без
  перекладки рамы 0°→55°. Сразу после арма — макс. команда pitch (крейсерский перехват).
- Метка приподнята: при постоянном θ начальный угол места **β_start ≈ 30°** (не 45°:
  часть «наведения вверх» уже даёт наклон рамы); при сближении **β → 0°** (выход на горизонт).
- **Торможения нет. θ = 55° = const** на всей траектории.

### Принцип управления гимбалом
- **pitch — УПРАВЛЯЕМАЯ уставка β** (`ey → уставка β гимбала`, быстрый внутр. контур).
- **roll — фиксированная уставка 0**; гимбал парирует только крены (порывы, повороты).
  Курс правится yaw'ом (`ex → yaw`), крен не нужен.

### Расчёт хода гимбала (θ = const = 55°, наклонный старт)

При постоянном θ гимбал **не компенсирует** изменение наклона рамы — θ входит только в
абсолютную позицию серво. Ход = **Δβ** по углу места.

**Почему ход меньше, чем при «горизонтальном» старте (45°):**
1. Нет фазы θ: 0°→55° — гимбалу **не нужно** отрабатывать перекладку рамы в крейсер
   (в старой схеме это добавляло до ~55° компенсации по серво).
2. При θ = 55° с первой секунды линия визирования на приподнятую метку имеет меньший
   **β_start ≈ 30°** (геометрия пикирования), а не 45°.

| Момент | β | θ | Серво (отн. рамы) |
|---|---|---|---|
| Старт (далеко) | **30°** | 55° | **85°** |
| Промежуток | 15° | 55° | **70°** |
| Прибытие (β→0°) | 0° | 55° | **55°** |

**Ход по pitch = β_max − β_min = 30° − 0° = 30°** (серво **55°…85°** отн. рамы; ранее
при β_start=45° было 45° и диапазон 55°…100°).

**Ход по roll = ±20…25°** (уставка 0°, парирование порывов; запас можно чуть снизить).

### Монтаж камеры на раму

Середина рабочего диапазона при наклонном старте:
\(\alpha_{mount} = 55° + 30°/2 = \mathbf{70°}\) от плоскости рамы (нос вверх).
Серво ходит **±15° от нейтрали** (β=15°). Альтернатива: крепление при 55° отн. рамы —
серво от 0° до +30° в одну сторону.

### Тяговооружённость T/W = 10:1 и скорость

Скорость задаёт лобовая площадь, не T/W: \(v=\sqrt{2mg\tan55°/(\rho C_dA)}\).
- T/W=10 ≫ потребного 1.74 → тяга не ограничитель; удержание высоты до θ=84.3°.
- Разгон \(a=g\tan55°\approx 1.4g\); для «грязного» квада ~24 м/с, для обтекаемого
  корпуса (Red Bull-чейзер, DRL Racer X) — до 300 км/ч при том же 55°.
- Ограничитель у нас — аэродинамика планера и видео-контур, не тяга.

### Старт: наклонное армирование

θ = 55° = const ⇒ коптер нужно армировать **уже под углом 55°** (ручной бросок/наклонная
площадка). Проверка армирования `"Leaning"` в ArduPilot: `lean > ATC_ANG_MAX`; при
`ATC_ANG_MAX=55°` проверка строгая (`>`), значит ровно 55° **допускается**. На практике:
установить `ARMING_SKIPCHK` бит INS (бит 4, значение 16) чтобы исключить случайный отказ
при θ=55.x°. После арма Pi **немедленно** подаёт максимальную команду CH2 (pitch вперёд)
— фазы висения нет, коптер сразу в крейсерском режиме.

### Следствие для управления (финальная схема осей)
| Ось | Сигнал | Описание |
|---|---|---|
| Pitch гимбала | `ey → β` | Быстрый внутр. контур: держит метку по вертикали кадра |
| Roll гимбала | уставка 0 | Стабилизация горизонта (FC, AP_Mount_Servo) |
| CH1 Roll коптера | PID | Горизонтальный доворот |
| CH2 Pitch коптера | макс. вперёд + anti-sat | Удержание max скорости; отступает при сатурации гимбала |
| CH3 Throttle | внешн. контур | Удержание высоты |
| CH4 Yaw | `ex → yaw` | Азимутальный доворот к метке |

## 7. Возможные развилки на будущее

## 8. Стенд этап 1 (Pi 5, без SBUS) — ПРИНЯТО

**Цель:** увидеть вживую работу алгоритма **обнаружения и сопровождения** метки.

**Не делаем на этапе 1:** SBUS, RP2040, полётник, дальняя метка 1.5 m.

### Аппаратура
- **Pi 5** + MIPI-камера на **двухосевом гимбале**.
- Сервоприводы **MG946R** (pan/azimuth + tilt) через плату **PCA9685** (I2C, 50 Hz PWM).
- **PAL-монитор** (composite J7) — оператор видит кадр с OSD.
- **Метка-имитатор:** белый лист с контрастной точкой/фигурой перед камерой.

### Поведение
- Детект тёмного blob на белом фоне (`marker_detector`, `THRESH_BINARY_INV`).
- Ошибки `ex`, `ey` (смещение метки от центра кадра).
- **PID** → углы pan/tilt гимбала; при сдвиге листа камера поворачивается,
  удерживая метку в поле зрения.
- OSD: рамка, ex/ey, pan/tilt, статус TRACK.

### Подключение серв (PCA9685)
- Pi I2C: SDA/SCL (pins 3/5), `dtparam=i2c_arm=on`, адрес **0x40**.
- MG946R: pan → канал 0, tilt → канал 1; питание 5 V на V+ платы, общая GND.
- Драйвер: `pca9685.*` + `servo_gimbal.*` (50 Hz PWM, импульс 1000–2000 µs).

### ПО
Каталог `sbus_capture/bench/`, бинарник `electronic_pilot_bench`.

**Трекинг (актуально):** `MarkerTracker` — motion-refine, weighted NCC, адаптивный шаблон.
Спецификация: [`bench/TRACKING_ALGORITHM_SPEC.md`](bench/TRACKING_ALGORITHM_SPEC.md).
MOSSE — только в git tag `epilot-snapshot-*`.
